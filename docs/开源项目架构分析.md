# 开源项目架构分析：Chubby 的同位者 etcd

## 选型说明

| 候选 | 不选为主分析对象的理由 |
|---|---|
| ZooKeeper | 最像 Chubby（ZNode + 锁 + session），但用 Zab 而非 Paxos，只能类比不能对照 |
| Consul | 定位是服务发现与网格，KV 只是配套，核心不在共识层工程 |
| Doozer | 早期"开源 Chubby"，但已停止演进，撑不起关键代码级分析 |
| PhxPaxos | 微信开源的 Paxos **库**，缺会话、租约、Watch、存储引擎这些系统级部分 |
| **etcd** | **选它**：与 Chubby 定位最像；用 Raft 取代 Paxos 正对本章主题；Go 可读性好；云原生事实标准（Kubernetes 元数据后端） |

ZooKeeper 更像 Chubby 的"形"，etcd 更像"神"——两者都把"一小块强一致元数据 + 会话/租约 + 变更通知"做成基础设施，只是共识层换了 Raft。

---

## 一、项目定位

**Chubby** 是 Google 的粗粒度分布式锁服务，附带小文件存储：客户端通过 **session（keepalive）** 与 5 副本的 Paxos 组保持联系，在文件/目录粒度上加**粗粒度锁**，用 **sequencer** 把"我持锁"变成可传递的凭证。它服务 GFS、Bigtable 这类系统的选主与元数据，是低频但极重要的控制面。

**etcd** 的官方定位是"为分布式系统保存最关键数据的可靠键值存储"，对外是 gRPC 的 KV / Watch / Lease / Txn，被 Kubernetes 用来存整个集群的期望状态。它同样不追求高吞吐数据面。

两者解决的问题一一对应：**粗粒度锁**、**元数据/配置**、**选主**、**服务发现/成员信息**、**变更通知**。

| 维度 | Chubby | etcd |
|---|---|---|
| 定位 | 锁服务 + 小文件（控制面） | 强一致 KV，元数据基础设施（控制面） |
| 一致性协议 | Paxos 多副本组 | Raft（自研 `raft/`，独立 Go module） |
| API | 类文件系统：open/get/set/delete + acquire/release + sequencer | gRPC：Put/Range/Txn/Compact + Watch（流）+ Lease |
| 会话机制 | session + keepalive，过期释放其锁 | lease（TTL）+ KeepAlive，到期回收其挂载的 key |
| 典型用户 | Google 内部：GFS、Bigtable、MapReduce | Kubernetes、CoreDNS、Calico、TiDB |
| 部署规模 | 建议 5 副本 | 官方 FAQ 建议不超过 7 个成员，生产常见 3/5 节点，并引 Chubby 的 5 副本为参照 |

> 口径说明：etcd 的"不超过 7 个成员""奇数节点"均出自官方 FAQ 原文。本机无法直连 `raw.githubusercontent.com`，文档正文与源码经 Debian 源码镜像和 gitee 的 `etcd-io/etcd` 镜像读取，链接见第十一节。

## 二、整体架构分层

一句话：etcd 把"共识 → 日志 → 状态机 → 存储引擎"彻底解耦，外面包一层 gRPC。

- **客户端** `client/v3`：连接管理、重试、事务封装。
- **API 层** `server/etcdserver/api/`、`v3_server.go`：协议翻译、鉴权、限额、挂载流式 Watch。
- **etcdserver** `server/etcdserver/server.go`：串起提案、apply、配额告警、选主后的租约晋升。
- **raft** `raft/`：纯算法，不碰网络与磁盘；输入消息与 tick，输出 `Ready`。
- **WAL** `server/storage/wal/`：raft 的硬盘记忆，崩溃靠它重放。
- **MVCC** `server/storage/mvcc/`：真正的状态机，key 带 revision，可读历史、可 compact。
- **bbolt** `server/storage/backend/`：B+ 树引擎，提供页级事务与批量提交。

```text
  客户端 client/v3 · etcdctl · kube-apiserver
        │ gRPC: KV / Watch / Lease / Txn
  API 层  server/etcdserver/api, v3_server.go     鉴权·限额·流式 Watch
        │
  etcdserver  server/etcdserver/server.go         提案·apply·成员·租约晋升
        │     └── raftNode (server/etcdserver/raft.go)
        │ Ready(): Messages / Entries / HardState
  raft  raft/  选举·复制·ReadIndex·批量·流水线  ◄──► rafthttp 对等节点
        │ Save(HardState, Entries)   ← fsync 在这里
  WAL  server/storage/wal/  ($seq-$index.wal)     崩溃重放
        │ apply 已提交条目
  MVCC  server/storage/mvcc/  (revision + treeIndex)
        │
  bbolt  server/storage/backend/ + schema/        页级事务·批量提交
```

容易看漏的是：**WAL 与 MVCC 是两条并列的持久化路径**——WAL 存 raft 日志（含未 apply 的），MVCC/bbolt 存已 apply 的结果。恢复时先用 snapshot 建索引，再重放其后的 WAL，边界就是 snapshot。

## 三、关键代码导读

只写"文件负责哪条流程"，不写行号与签名。

| 路径 | 负责什么 |
|---|---|
| `server/embed/etcd.go` | 进程装配：`StartEtcd` 校验配置、建 peer/client/metrics 监听、把 `Config` 翻成 `etcdserver` 的 `ServerConfig`。源码中可见 `UnsafeNoFsync`、`PreVote` 在此传递 |
| `server/etcdserver/server.go` | 服务主体：持有 raftNode、MVCC、lessor、配额告警；把请求变成提案、把已提交条目驱动到 apply；选主后把本地 lessor 提升为 primary 接管租约回收 |
| `server/etcdserver/v3_server.go` | 对外 RPC 实现：写请求走"提案 → 等结果"，需要线性一致的 Range 走 ReadIndex。官方 FAQ 明写发到 follower 的共识请求会被转给 leader |
| `server/etcdserver/raft.go` | 粘合层：`raftNode` 跑 `ticker + Ready()` 循环，更新 leader、派发 ReadStates、把已提交条目交给 apply，再 `SaveSnap`/`Save`/`Advance`。**leader 先发消息再落本地盘**（注释指明取自 raft 论文 10.2.1） |
| `raft/` | 共识本体：`Step(msg)` 推状态、`Tick()` 推时钟、`Ready()` 吐出待持久化与待发送内容；含选举、`MsgPreVote`、批量、流水线、`ReadIndex`、失去多数派自动退位，`MustSync` 判断是否必须 sync |
| `server/storage/wal/` | 预写日志：文件名 `$seq-$index.wal`，超 64MB 切分（包注释写明），每条记录带 64 位长度头 + CRC32；`Save` 追加状态与条目，`SaveSnapshot` 记快照边界，`ReadAll` 启动读回 |
| `server/storage/mvcc/` | MVCC：key 按 revision 存多版本，内存 `treeIndex` 管版本链，key-value 在 backend；`store` 维护 `currentRev`/`compactMainRev`，`restore` 重建索引，compaction 回收旧版本 |
| `server/storage/backend/`、`schema/` | bbolt 封装与元数据布局：读/写/批量事务，以及 lease、key、meta 的 bucket 常量 |
| `server/lease/` | 租约：`lessor` 管 Grant/Revoke/Renew/Attach；**primary lessor 就是 raft leader**（注释明说）；只持久化 lease ID 与 TTL，挂载的 key 从 KV 反查；换主时把剩余 TTL checkpoint 进共识日志 |

一个很能代表工程取向的细节：**raft 包完全不碰磁盘与网络**，只产出"要我存什么、要我发什么"。好处是同一份 raft 能用内存存储反复单测，不必起集群。

## 四、一次写请求的完整链路

以 `etcdctl put a 1` 为例：

1. 客户端编码 protobuf，经 gRPC 发往任意成员；非 leader 节点转给 leader，leader 不可达就尽快失败让客户端重试。
2. API 层鉴权、校验大小与 Txn 操作数，包成内部 `InternalRaftRequest`，再由 leader 追加一条日志（index 单调递增）。
3. 复制：leader 发 `MsgApp`，follower **先写自己的 WAL** 再回 `MsgAppResp`。**【批处理】** 一次 `MsgApp` 可带多条 entry，`MaxInflightMsgs` 允许多批在途即**流水线**。
4. 提交：收到多数派（`n/2+1`）回包后标记 committed。
5. 落盘：`raftNode` 调 `Save(HardState, Entries)`。**【fsync】** 就在这一步，`MustSync` 决定是否必须 sync（term/vote/commit 未动时可省）。第 3、5 步在 leader 上**并行**——先发后存，别让本地磁盘拖住复制。
6. apply：条目进入 MVCC（写新 revision、更新 treeIndex、写 bbolt）。**【批处理】** bbolt 用 `BackendBatchLimit`/`BackendBatchInterval` 把多个 apply 合并成一次事务提交，摊薄写事务代价。
7. 返回：apply 完成后才回响应。对客户端而言"成功"= 多数派已持久化 + 本地状态机已更新。

**【两阶段（预投票/投票）】** 只出现在**换主**路径，不在写入路径：raft 支持 `MsgPreVote`/`MsgPreVoteResp`，预投票**不增加 term**，只探询"我竞选你们会投我吗"，过关才真正投票并抬升 term；etcd 用 `PreVote` 配置暴露（见 `server/embed/etcd.go`）。少了它，被隔离很久、term 被自己抬高多次的节点回归时会把整个集群 term 顶上去，逼出无谓重选。

| 特殊步骤 | 位置 | 作用 |
|---|---|---|
| **fsync** | WAL `Save`（每副本各一次） | 让"已提交"在掉电后仍成立 |
| **批处理** | raft 消息/条目批量 + bbolt batch 提交 | 一次系统调用/一次 fsync 摊到多条请求 |
| **两阶段** | 仅选举路径 PreVote + Vote | 防被隔离节点用高 term 打断稳定集群 |

## 五、持久化与崩溃恢复

**WAL 的作用**：raft 要求"投过票、承诺过的日志"不能因重启消失，WAL 就是这条承诺的载体——先写日志，再改内存，最后才说"已提交"。etcd 的 WAL 分段（`$seq-$index.wal`），超 64MB 切分，每条记录带 CRC，末段损坏最多丢末尾不完整记录。

**snapshot 的作用**：只留 WAL 会无限增长，重启要重放全部历史。于是定期把完整状态做成快照并在 WAL 记边界，`--snapshot-count`（默认 100000 个已提交事务）是阈值；有了快照，旧 WAL 段可释放，新成员可直接收快照追赶。恢复流程即 **snapshot → 重建 MVCC 索引 → 重放其后的 WAL**。顺序有硬约束，`raftNode` 注释写得很直白：必须**先**保存 snapshot 文件与 WAL 里的快照记录，**再**保存任何 entries 与 hardstate。

**`--unsafe-no-fsync` 意味着什么**：关掉 WAL 的 fsync，写入只到页缓存，"committed 即持久"不再成立——掉电时已回复客户端的写可能消失，甚至回退到更旧的 term/commit。官方文档把这类参数单列为 **Unsafe flags**，明确警告"会破坏共识协议给出的保证"。它只为对照实验存在。

这正是我们实验的 `--fsync on|off`：`paxos/storage.py` 的 `Journal` 有三档——`fsync`（write+flush+os.fsync）、`flush`（只到内核页缓存）、`buffer`（用户态缓冲，累计 4KiB 才 flush）。`off` 走 `buffer`，`kill -9` 时未落盘记录直接消失，重启后 `promised_id` 回退。结论与 etcd 一致：**fsync 不是性能选项，而是正确性的一部分**。

## 六、会话与租约

Chubby 的核心抽象是 **session + 锁**：session 活着锁就活着，session 过期（崩溃、断网、GC 停顿过长）锁自动释放。陷阱是客户端可能"以为自己还持锁"，所以 Chubby 用 **sequencer** 让下游能校验凭证是否过期。

etcd 没有这两个原语，用三件东西等价拼出：

1. **lease（TTL）** = session 生命周期：`LeaseGrant` 给 TTL，客户端须周期 `LeaseKeepAlive`，否则到期回收。
2. **事务（Txn + Compare）** = 加锁的原子性：比较 `create_revision == 0`，只有 key 不存在才写成功，这就是互斥锁。
3. **Watch（流）** = 等锁队列：抢不到就 watch 该 key，删除事件一到重试；要公平锁就 watch 前一个 revision。

```text
acquire(lease): txn(if create_revision("/lock/x")==0
                      then put("/lock/x", me, lease=lease) else fail)
                失败则 watch("/lock/x") 直到被删除，再重试
release:        delete("/lock/x")   // 或让 lease 过期
```

**为什么租约必须绑心跳**：TTL 的语义是"最后一次续约 + TTL"，没有心跳就没有"活着"的证据。不绑心跳的话，持锁者崩溃后锁永不释放（死锁）；靠"猜测"释放又不安全。把"是否活着"交给**客户端主动续约 + 服务端计时**，是唯一不需要额外故障检测器的做法。

两个细节：**过期回收必须走共识**——到期要删掉它挂的所有 key，这是状态变更，必须 leader 提案、多数派确认，否则各副本 KV 会分叉；这也是"primary lessor = leader"的原因。**换主时 TTL 不能重置**，否则刚过期的锁会因换主"复活"；etcd 把剩余 TTL checkpoint 进共识日志，新 leader 按剩余值续期。

## 七、选主与故障恢复

**term（任期）** 是 raft 的逻辑时钟：每次选举 +1，大者压倒小者；投票时检查"你的日志至少和我一样新"，保证新 leader 含所有已提交条目。

**一次换主要多久**：etcd 默认 `--heartbeat-interval` 100ms、`--election-timeout` 1000ms。follower 超时没收到心跳就发起选举，典型不可用窗口 ≈ **一个 election timeout + 一次选主 RTT**，量级一秒上下。跨数据中心时官方建议 heartbeat 接近 RTT、election-timeout 至少为其 5 倍。

**为什么建议奇数节点**：quorum = `n/2+1`，可容忍故障 = `n - quorum`。官方 FAQ 的对照：

| 集群规模 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|
| 多数派 | 2 | 3 | 3 | 4 | 4 |
| 可容忍故障 | 1 | 1 | 2 | 2 | 3 |

**4 节点为什么没有额外收益**：quorum 从 2 变 3，可容忍故障仍是 1，但"可能坏掉的节点"多了一个，可用性算术上更差；每次提交还要多等一个回包。

我们自己的数据印证了这点（`results/faults.csv`，Multi-Paxos，8 并发，杀的都是**非 Leader** 的 Acceptor）：

| 场景 | 最长黑洞(ms) | 恢复(ms) | 换主次数 |
|---|---|---|---|
| 3 节点，杀 1 个非 Leader Acceptor | 335.0 | 63.9 | 3 |
| 4 节点，杀 1 个非 Leader Acceptor | 2.9 | 89.4 | 4 |

3 节点那次 335 ms 的黑洞来自"恰好有一批 Accept 在途，要等 `attempt_timeout` 超时才能换一组多数派"；
4 节点因为还有两台可以立刻答应，几乎没有等待。中断窗口不能简单按"节点数越多越好/越差"推断，
**它取决于故障时刻的在途请求与多数派构成的交集**——这比教科书上的 quorum 算术更接近工程现实。

## 八、性能工程

- **批处理**：三个层次——多个 `MsgApp` 合并发送、多条 entry 打进一个 `MsgApp`、多个 apply 合并进一个 bbolt 事务。目标都是"一次系统调用/一次 fsync 覆盖更多请求"。
- **流水线**：`MaxInflightMsgs` 让多批复制同时在途；更进一步是**先发消息再写本地盘**，让本地 fsync 与网络 RTT 重叠，对尾延迟影响最大。
- **只读不进日志**：默认线性一致读走 **ReadIndex**——leader 先向多数派确认自己仍是 leader，拿到 read index，等本地 apply 到该 index 后直接读 MVCC；follower 也能提供（向 leader 要 read index 后本地等待）。raft README 还提到基于租约的读，代价是**依赖各机时钟**，属可选优化。
- **Watch 用 gRPC 双向流**：一连接挂多个 watch，按 revision 推事件，断线可从上次 revision 续传；只读 MVCC 历史，不影响写路径。
- **bbolt 写事务代价**：单写者、页级 copy-on-write、提交要 fsync（数据页 + meta 页），还有 freelist 开销；所以 etcd 宁可合并 apply 提交，长期运行需 `defrag` 回收碎片。

一个直接相关的旁证：官方 FAQ 把磁盘延迟算进 leader 存活判定——leader 一次 WAL fsync 若耗时一分钟而 election timeout 只有一秒，它虽仍在发心跳，实际已无法提交，被换掉是"有意为之"。我们实验里 100ms 的 `attempt_timeout` 让 32 并发 Basic Paxos 直接活锁，是同一道理的另一面：**超时预算必须覆盖最慢那次 fsync**。

| 维度 | etcd | `paxos-lab`（代码依据） |
|---|---|---|
| 一致性协议 | Raft：选举 + 日志复制，`raft/` 为独立 module | 三种可切换：Basic / Multi-Paxos / Fast Paxos（`paxos/proposer.py` 三个子类） |
| 提案/日志编号 | term + 日志 index | `Ballot(round, node)` 字典序比较（`ballot.py`）+ slot 作实例号 |

| fsync 策略 | 每次 WAL `Save` 后 sync（`MustSync` 判必要性） | `--fsync on` 每条 write+flush+os.fsync；`off` 时 4KiB 用户态缓冲 |
| Leader 机制 | raft 选举，term 单调，PreVote 防抖动 | Multi-Paxos 用一次"覆盖全部实例"的 Prepare 抢 epoch，心跳广播身份（`ensure_leader`） |
| 快速路径 | 无（Raft 固定一轮复制换简单） | Fast Paxos 客户端直投，仲裁集 ⌈3n/4⌉（`fast_quorum_size`），冲突回退经典轮 |
| 批处理 | raft 消息/条目批量 + bbolt 批量提交 | `--batch-ms`/`--batch-size` 攒批，一次 Accept 带多条 entry，日志合成一条只 fsync 一次 |
| 故障恢复 | snapshot 恢复 + WAL 重放 + 新成员快照追赶 | Acceptor 重放恢复承诺；Leader 空槽修复（原值或 noop）；Learner 缺口回填 `learn_ask` |
| 消息数 | 每提案一轮 `MsgApp`/`MsgAppResp` + 100ms 心跳 | `transport.Counter` 统计 sent/recv/dropped/by_type，写进实验 CSV |
| 语言/规模 | Go，多 module，工程量远超本实验 | 纯 Python 标准库，`paxos/` 约 3300 行 + `experiments/` 约 1400 行（非空行） |
| 只读路径 | ReadIndex / follower read，不写日志 | 无（读本地状态机，不保证线性一致） |
| 会话/租约 | lease + Txn 组合出分布式锁 | 无（只有 `req` 幂等键去重，见 `kv.py`） |

最刺眼的是最后两行——恰是 Chubby 类系统的产品价值所在，也是本实验没覆盖的部分。

## 十、五条可迁移的工程启发

**1. 超时不等于丢权。** `MultiPaxosProposer._run_batch` 里只有**某个 Acceptor 明确回报更高提案编号**才 `step_down`，单纯超时只重试同一批。我们早期把任何超时都当"被顶掉"，结果一次慢 fsync 就触发让位 → 重选 → 在途请求全失败。etcd 同构：Acceptor 的拒绝携带 `promised`，没有编号的沉默只能算"不知道"。

**2. 只有 Leader 才有资格做空槽修复。** `_repair_loop` 用 Leader 的 `epoch` 对空洞幂等重跑 Phase 1，取别人可能接受过的值，没人接受过就填 noop。修复本质是"用更大编号盖掉旧提案"，若每个节点都去盖会互相作废——与 etcd"只有 leader 发起 lease 回收提案"同构：**收敛点必须唯一**。

**3. 把冲突交给 Leader，是用延迟换确定性。** Basic Paxos 各节点自己 `alloc_slot`，撞车必然，我们靠随机退避 + 跳 slot（`skip_slots`），冲突率直接变成长尾；Multi-Paxos 只让 Leader 分配 slot，冲突从根上消失；Fast Paxos 反其道，省一跳但冲突率成了核心指标。三种机制正好构成"冲突放哪里"的谱系。

**4. Learner 的日志不需要 fsync。** `node.py` 里 Acceptor 用 `fsync`、Learner 用 `flush`。理由写在 `storage.py`：`promised_id` 是安全性的根，丢了破坏正确性；Learner 的决定日志是**派生数据**，丢了可从同伴回填（`learn_ask`）。etcd 同构：WAL 必须 sync，快照后的状态与 watch 进度丢了可重建。**分清"源数据"与"派生数据"是划 fsync 边界的第一原则。**

**5. 平台时间精度会毁掉 RTT 实验。** `timer.py` 记录了最疼的坑：Windows 定时器精度 15.6ms，`asyncio.sleep(0.001)` 实际睡 15.6ms，而注入时延是 RTT/2（RTT=1ms 时仅 0.5ms），"注入 1ms"变成"注入 15.6ms"，整条曲线横轴全废；且 `timeBeginPeriod(1)` 只在前几秒有效。最终方案是"睡大头 + 自旋收尾"的混合睡眠，批处理循环也从 `sleep` 轮询改成 `Event` 唤醒。同源教训：不开 `TCP_NODELAY` 时 Nagle + 延迟 ACK 会让 1ms RTT 的 P50 从 2ms 涨到 40ms——**做延迟实验前先校准测量工具**。

## 本章小结

- **定位同构**：Chubby 与 etcd 都是控制面基础设施，解决锁/元数据/选主/配置/服务发现五件事；区别在共识层——Paxos vs Raft，"可理解性"本身就是工程目标。
- **分层解耦是核心设计**：raft 只算不写、WAL 只写不算、MVCC 只管状态机、bbolt 只管页，层间只靠 `Ready()` 与"已提交条目"两个很窄的接口连接，每层可单独测试与替换。
- **正确性由 fsync 边界决定**：WAL 的 `Save` 是唯一必须 sync 的地方，snapshot 解决日志回收与新成员追赶；`--unsafe-no-fsync` 之所以"absolutely unsafe"就是拆掉了这条边界，与我们 `--fsync off` 的结论一致。
- **性能全部来自"藏延迟"**：批处理摊薄 fsync、流水线与"先发后存"重叠 RTT、ReadIndex 让只读不进日志、Watch 走独立流，没有一条靠改算法换。
- **规模算术比直觉可靠**：`n/2+1` 决定了 4 节点不比 3 节点更容错、恢复反而更慢；`faults.csv` 里 85ms vs 322ms 的 blackout 差距就是这条算术的实测版。
